# Playwright UI + API Framework — Project Rules

> Read at the start of every session.
> Target: Toolshop demo store. UI at `https://practicesoftwaretesting.com`,
> API at `https://api.practicesoftwaretesting.com` (OpenAPI document at `/docs`).

## Language policy

- Respond in the language the specialist writes in
- All project artifacts — code, comments, docs, skills, rules, checklists, test

## Project structure

```
├── config/env.ts            ← ONLY place that reads process.env
├── core/
│   ├── run-user.ts          ← the account THIS RUN owns — basis of all isolation
│   ├── global-setup.ts      ← register user → UI login → data snapshot → OpenAPI spec
│   ├── global-teardown.ts   ← remove favorites, then the user (needs admin: 403 otherwise)
│   ├── allure-labels.ts     ← parses `[Section / SubSection]` titles into report structure
│   └── allure-categories.ts ← failure triage buckets for the report
├── api/
│   ├── generated/schema.d.ts ← GENERATED by `npm run api:types`. Never edit by hand
│   ├── types.ts             ← domain types derived from the schema, narrowed deliberately
│   ├── client.ts            ← openapi-fetch: paths and params typed from the spec
│   ├── contract.ts          ← spec validation + discovery of the operations api/ calls
│   ├── traffic.ts           ← records API calls, redacts secrets, renders them with curl
│   ├── expect.ts            ← status assertions that print the response body
│   └── *.api.ts             ← typed clients over api/client.ts
├── pages/
│   ├── components/          ← elements that live on every page (header)
│   └── <area>/              ← Page Objects: locators as private getters, extend BasePage
├── fixtures/base.fixture.ts ← ALL fixtures; always import test/expect from here
├── data/                    ← routes + UI labels; no hardcoded strings anywhere else
├── utils/                   ← logger, data snapshot
├── tests/tags.ts            ← the only place a tag exists; `npm run check:tags` enforces it
├── tests/<feature>/         ← grouped by FEATURE, layer is the filename suffix:
│      *.api.spec.ts         ← project "api" — no browser is launched
│      *.ui.spec.ts          ← project "ui" — authenticated via storageState
│      *.hybrid.spec.ts      ← API creates state → UI verifies (the showcase pattern)
├── docs/                    ← artifacts of the pipeline, keyed by task (see below)
│   ├── context/<feature>/context.md  ← verified locators + API fields — belongs to the
│   │                                   FEATURE, merged, lives for years
│   ├── checklists/checklist_<key>.md ← QA checklist — belongs to the TASK
│   ├── test-cases/cases_<key>.md     ← test cases with Automation notes (from /cases)
│   └── plans/plan-<key>.md           ← automation plan (from /autotests, phase 2)
└── .claude/                 ← rules/, skills/, agents/, hooks/, settings.json
```

## The five things that matter most

Full reasoning in `.claude/rules/architecture.md`. The short version:

1. **Every run registers its own user.** The suite never uses the shared demo
   customer. This is what makes `fullyParallel: true` honest instead of optimistic.
2. **Isolation first, parallelism second, `retries: 0`.** A retry hides a race and
   defers the diagnosis to the worst possible day.
3. **API types are generated from the live OpenAPI spec**, and contract tests verify
   the server actually matches it. Generated types are a claim; contract tests are
   the proof.
4. **JWT lives 300 seconds.** Always `getToken()` at the point of use, never a stored
   token, never a shared token file.
5. **Locators are never invented.** They come only from `docs/context/<feature>/context.md`.
   Missing → report it, do not guess.

## Core conventions

Full version: `.claude/rules/conventions.md`. Non-negotiables:

- `test`/`expect` — ONLY from `fixtures/base.fixture`
- Specs live in `tests/<feature>/` and the layer is the **suffix**: `.api` / `.ui` /
  `.hybrid`. Projects match the suffix, not the folder — a feature keeps all three
  layers side by side
- An element that appears on every page belongs in `pages/components/`, composed by
  the page objects that need it — not copied into whichever page needed it first
- Locators — ONLY `private get` getters in page objects; never in spec files
- Locator priority is by **stability**: real `id` → `data-test` → `getByRole` →
  stable class → CSS/XPath. In this app `data-test` wins in practice because
  coverage is near-total — that is a property of this app, not a universal rule
- Select by value, not visible text (the app ships eight locales)
- Strings/routes from `data/`; `process.env` only in `config/env.ts`
- API paths are NEVER strings. `client.GET('/products/{productId}', ...)` is checked
  against the generated schema; a path or query param that is not in the spec does
  not compile
- Every test: `[Section / SubSection]` describe + at least one tag from `tests/tags.ts`
  (`{ tag: [TAGS.api, TAGS.smoke] }`) — the Allure report parses both, and a raw
  `'@smoke'` literal is refused by `npm run check:tags`: a mistyped tag does not fail,
  it silently drops the test out of the filtered run
- Status checks on `*Raw` responses go through `api/expect.ts` — they print the response
  body, and a validation test names the field it expects to be rejected
- `@demo` marks the three tests that fail **on purpose** (`tests/*/demo-failure.spec.ts`).
  They document what a failure looks like in the report. Never "fix" them, never skip
  them, never copy their pattern into a real test. They run locally and are excluded
  in CI (`grepInvert` in `playwright.config.ts`)
- No `waitForTimeout` — wait for responses or element state
- Anything created carries `RUN_ID` and is cleaned up in `afterAll`

## The pipeline

Six commands, three agents, and rules they all read. One argument ties the whole chain
together: a **key** — a tracker id (`PROJ-431`) or a feature name (`checkout`). Every
stage resolves its inputs from it, so nobody passes file paths around.

| Command             | Model  | What it does                                                                        |
| ------------------- | ------ | ----------------------------------------------------------------------------------- |
| `/setup`            | sonnet | Fresh clone → green run: toolchain, deps, browser, reachability, smoke              |
| `/checklist <key>`  | sonnet | Ticket (or description) → verified against the running app → checklist + context.md |
| `/cases <key>`      | opus   | Checklist → test cases with Automation notes                                        |
| `/autotests <key>`  | sonnet | Plan (with a gate) → page objects + specs → takes them green                        |
| `/test-code-review` | opus   | This project's rules — the part no general reviewer can know                        |
| `/commit-push`      | haiku  | Commit with confirmation; push only after explicit approval                         |

What is deliberately NOT a command:

- **The key and the handoffs** — `.claude/rules/pipeline.md`: what `<key>` is, which
  artifact belongs to the task and which to the feature, how a key is derived when none is
  given, and what each stage does when its input is missing (it stops and names the
  command that produces it, never guesses the scope).
- **Running and fixing tests** — `.claude/rules/running-tests.md`. It contains no
  decision: "run it, read the error, one focused fix, stop after two" is the same
  procedure whoever runs it. `/autotests` reads it in phase 6, `/test-code-review` reads
  it when reproducing a finding. A procedure with no human gate is a rule, not a button.
- **Exploring the app** — the `explorer` agent, called from inside `/checklist`. It is
  needed in the middle of other work, not as a thing a human presses.

The dividing lines used here, in case a new piece needs placing:

| It is a | when                                                     |
| ------- | -------------------------------------------------------- |
| skill   | there is a point where a human decides something         |
| rule    | it is knowledge several skills need                      |
| agent   | it needs its own context window, or narrower permissions |
| hook    | it is a prohibition that cannot be left to memory        |

`/test-code-review` is deliberately **not** named `code-review`: a project skill with that
name replaces the bundled `/code-review` entirely. Both are wanted — the bundled one finds
general correctness bugs, this one knows about `PRODUCT_ALLOCATIONS`, the 300-second JWT
and the `guest` context. Run both. The name says test **code**: the review of test cases
and checklists happens earlier, in `/cases`.

`/commit-push` refuses to run until `/test-code-review` has recorded a clean review of
exactly this diff (`.claude/scripts/review-marker.mjs`). Fix, review again, then commit.

Models are pinned per skill: judgment steps get Opus, spec-following steps get Sonnet,
mechanical steps get Haiku. Sub-agents in `.claude/agents/` follow the same logic —
`explorer` (sonnet), `test-writer` (sonnet), `reviewer` (opus) — and are restricted by
their `tools` list, which is what makes their boundaries real: `explorer` drives the
browser through Playwright MCP but cannot touch `tests/`, `test-writer` writes code but
cannot run the suite.

Invocation is controlled per skill, not left to chance: `description` says what the skill
does, `when_to_use` carries the phrases that should trigger it, and `commit-push` sets
`disable-model-invocation` because nothing should decide on its own that the code is ready
to push.

Two rules are enforced by hooks rather than by prose (`.claude/settings.json`): editing
`api/generated/`, `.env`, `.auth/` or the lockfile is refused outright, and so are
`--force`, `--no-verify` and `--amend`.

Browser target: `UI_BASE_URL` / `API_BASE_URL` in `config/env.ts`, overridden in `.env`.
Point them at a local stand or a test environment and the whole pipeline follows — no
hostname lives anywhere else.

## Git rules

- NEVER commit or push without explicit permission ("commit", "push" from the specialist)
- Never commit `.env` or `.auth/`
- DO commit `api/generated/schema.d.ts` — CI compares it against the live spec
- Temporary scripts go to `tmp/` (gitignored), never the project root

## Running

```bash
npm install && npx playwright install chromium   # first time
npm test                                          # full suite (~30s) — 34 pass, 3 @demo fail
npm run test:green                                # everything except the @demo failures
npm run test:demo                                 # only the three deliberate failures
npm run test:smoke                                # @smoke only
npm run test:api                                  # API project — no browser
npm run api:types                                 # regenerate types from live spec
npm run report:allure                             # Allure report
npm run gates                                     # typecheck + lint + format + tags
```

A failing test attaches `api-traffic` (every API call it made, bodies included, secrets
redacted, each with a `curl` that replays it) and, for browser tests, `browser-console`.
Read those before opening the trace.

# Plan: auth

Status: implemented
Sources: [cases_auth.md](../test-cases/cases_auth.md) · [context.md](../context/auth/context.md)

A worked example of the plan that the implementation stage stops at. Everything below is
decided **before** a line of test code is written, because each of these is expensive to
change afterwards: the data slices determine whether the file is parallel-safe, and the
cleanup owner determines whether teardown can succeed at all.

## Data plan

- **Snapshot picks:** none — auth needs no product data
- **Distinct slices:** every test acts as `runUser`, which is unique per run. No two
  tests here create a second account except the registration specs, which build their
  own via `buildApiUser('<prefix>')` with a distinct prefix each
- **Live API state:** the profile tests mutate the run user's own profile; the values
  carry `RUN_ID` so concurrent runs cannot read each other's
- **Namespacing:** `RUN_ID` in every generated email and in the profile values
- **Cleanup:** accounts created by the registration specs are removed in `afterAll` **as
  admin** — a user cannot delete itself (403, verified). The run user itself is removed
  by global-teardown, not here

## Page object additions

`pages/auth/login.page.ts`

- `login(email, password)` — fills and submits
- `assertLoginSucceeded()` — waits for `/account` and `page-title`
- `assertLoginErrorVisible()` / `assertStillOnLoginPage()`

`pages/account/account.page.ts`

- `assertSignedInAs(fullName)` — reads `nav-menu`. This is the method that makes the
  login assertion mean something
- `signOut()` / `assertSignedOut()`

All locator values from `## data-test Attributes Map` in context.md: `email`,
`password`, `login-submit`, `login-error`, `nav-menu`, `page-title`.

## API client additions

`api/auth.api.ts` — `login()`, `getToken()` (in-memory, refreshes at 240s),
`decodeToken()` for the TTL assertion. All three endpoints are in the OpenAPI spec.

## Fixtures

`guest` — one fresh logged-out context holding the login, register and account page
objects. They share a single context deliberately: an earlier version handed out only a
guest `LoginPage`, the test then reached for the regular `accountPage`, and the
assertion ran against a browser that had never seen the login.

## Risks / open questions

- The 18-75 date-of-birth window and the breach check are documented only in the
  OpenAPI property descriptions. If either changes, the negative cases fail as a
  contract problem, not a test bug — read them that way
- `house_number` is required by the form and optional in the schema. The UI
  registration test must fill it or the submit sends nothing, which presents as a
  `waitForResponse` timeout and reads like a broken locator
- Context sections for auth were verified 2026-08-29. Re-check before extending this
  plan if that date is more than 30 days old
